---
title: "Persistence and recovery"
description: "Understand durable history, synchronized files, and interrupted work."
---

Conversations, accepted input, and tool results live in the installation database. Canonical project content lives in its storage service. A conversation's working files and ongoing host commands belong to its independently supervised workspace keeper.

| Data | Location |
| --- | --- |
| Conversations and accepted input | Installation database; the history of conversations idle for a while, in installation asset storage |
| Conversation search index: messages, tool calls and errors, secrets redacted ([`otti search`](/cli/otti#search-conversations)) | Installation database, erased with its conversation |
| Published project content | Canonical storage service |
| Current working files and command output | Conversation workspace and keeper |
| Saved attachments | Installation asset storage |
| Private command credential files | Keeper-managed temporary files |
| Application databases and external volumes | Your deployment destination |

A conversation nobody has opened or run for a while can keep its history in slower storage. It stays in the sidebar as before, with its whole history: the first time you open it again, or an agent or `otti` reads it, it can take a moment (usually under a second, a few seconds for very long conversations) while its history comes back. If that storage cannot be read just then, the chat says its history is temporarily unavailable, and `otti` answers with the same message; try again a few minutes later. A message you send from a chat that is already open waits and is sent once the history is back. If the stored copy is missing or damaged, the chat says its history is unavailable. Searching conversations never brings a history back: their search entries stay in the database.

A routine application release lets existing work remain with its owning generation while new work starts on the promoted generation. Reconnecting the UI reads accepted input and existing tool receipts; it does not repeat commands.

If a host or process fails, the conversation can become blocked until the original receipt is reconciled. Inspect the actual effect before issuing a new command, especially for deployments or other external changes. A new runtime cannot resurrect a process lost with its host.

If Octomerge is recovered from a backup, it goes back to an earlier point, and work done after that point is gone. Work that was running at that point doesn't continue by itself: each conversation that was working comes back stopped, with a notice in its transcript, and a tool call that was in flight reads as having an unknown outcome, because it may have run afterwards. Check what a stopped conversation was doing before you continue it. Scheduled sessions that came due in between are skipped. A banner at the top of the app names the point the recovery went back to; it stays for a week, or until you dismiss it. Open tabs show a notice and reload by themselves, so they don't go on showing work the recovery took back. A team's integrations keep their place in its [event feed](/cli/api-client#follow-the-event-feed): the events they missed read as truncated.

Workspace synchronization keeps the workspace's current files, not earlier versions of them, and is not a backup of every external database or arbitrary host file. Commit what you want to keep to a project's history. Installation operators must retain independent database and storage backups and account for new writes before restoring an earlier snapshot.

## Deleted data and backups

What you delete (a chat, a branch, a project or your account) is deleted at once and can't be restored. Octomerge keeps deleted data in its backups for up to 8 days so it can recover from a failure. A recovery never brings back something you deleted: what you deleted after the point a recovery goes back to is deleted again when the recovery finishes, and its backup copies then go within 8 days. Access you took away after that point stays taken away too. Shares you revoked, team members you removed or whose role you lowered, API keys you revoked, and environment variables, secrets and connections you deleted don't come back, and a secret you replaced keeps its new value. Files on your own workers aren't in Octomerge's backups.
